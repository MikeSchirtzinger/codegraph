## 1. The spec's §4 premise was wrong, measured

`specs/explain-v1.md` §4 claimed `resolved_by` "exists only as fixture-side
ground truth" and that "runtime output has no rule attribution". Both halves
are false on the tree as it stood.

Persistence exists in the full pass (`resolve_project`, via
`ResolvedEdgeRow.resolved_by`) and in the incremental pass (`write_updates`,
via `resolved_by = $rb{i}`), and the schema has carried the column since
`6382480`:

```
$ git log --oneline -S'resolved_by' -- src/index/resolve.rs
2cf8aeb perf(index): batch node/edge writes + resolver delete-and-reinsert (~3.5x faster)
7c71761 feat(resolve): R2m - Rust module-relative path resolution (crate::/self::/super::)
6382480 feat(index): canonical identity + deterministic resolver + incremental re-resolution (R0/R1/R4)
```

The claim was not accepted from reading. It was checked by mutation: strip
the write and see whether anything notices.

```
# mutation applied: ResolvedEdgeRow.resolved_by := String::new()
$ cargo test --release --test fixtures_integration
...
c-cpp: 7/18 case(s) failed:
  - edge a: resolved_by mismatch - got "", want "r3"
  - edge b: resolved_by mismatch - got "", want "r1"
  - edge e: resolved_by mismatch - got "", want "r6"
```

All 9 fixture projects fail. So binding attribution was already persisted
AND already enforced by `tests/common/mod.rs::check_edges`, and that

**What was actually missing**: everything a rule that did *not* bind did.

### 2b. Schema declarations for the two new fields

Ownership of `src/schema.surql` moved to this lane after the work above had
landed, with the instruction to add `DEFINE FIELD` entries because "the store
is SCHEMAFULL, so persisting `resolved_by` needs them". Two parts of that are
worth correcting before recording what was done, because they change what the
work is:

1. **`code_edge` is SCHEMALESS, not SCHEMAFULL** (`src/schema.surql:56`).
   `code_node`, `file_metadata`, `deleted_symbol`, `fingerprint` and
   `project_registry` are SCHEMAFULL; the edge table deliberately is not.
2. **`resolved_by` already had a `DEFINE FIELD`** and has had since before
   this lane (`src/schema.surql:76`), alongside `resolution_gen` and
   `candidates`.

Both fields were already stored as real typed values (`array<string>` and

# Follow-up, 2026-09-14 (L7 part two)

Three items from the orchestrator after L4 built on `9d719ea`. New commit,
not an amend, because L4's `14b9a70` sits on top.

## F1. The serde tag trap

`Step` holds its payload in a field named `fact`, and `Fact` was serde-tagged
under the key `fact` too, so a step serialized as:

```json
{"index": 1, "fact": {"fact": "node_exists", "node_id": "...", ...}}
```

The same word meant two different things one level apart. That is not just
ugly. A consumer reaching for `step["fact"]["node_id"]` and one reaching for
`step["node_id"]` both look right, and serde ignores unknown keys on the way
back in, so writing to the wrong level raises no error and changes nothing.
L4 hit exactly that: a tamper test aimed one level too high, the chain
verified clean, and the test passed while tampering with nothing. A vacuous
pass anywhere is bad; in a verifier's own suite it is the one failure that
invalidates everything the suite claims.

The discriminator is now `kind`:

```json
{"index": 1, "fact": {"kind": "node_exists", "node_id": "...", ...}}
```

Pinned by `a_step_serializes_with_an_unambiguous_kind_discriminator`, which
asserts `steps[].fact.kind` is a string AND that both confusable paths,
`steps[].fact.fact` and `steps[].kind`, are absent. Asserting the absences
is the point: the bug was never that the right path was missing, it was that
a wrong path looked plausible.

Every tamper test in `tests/explain.rs` now routes through `assert_tampered`,
which serializes the chain before and after the mutation and fails if they
are equal. A mis-aimed tamper is now loud rather than green.

## F2. JSON schemas

`schemars::JsonSchema` derived on `Chain`, `Step`, `Fact`, `FindingKind`,
`EdgeKey`, `DeletedSymbol`, `Membership`, `StepVerdict` and `ChainVerdict`,
so `codegraph_verify_chain` can publish a real input schema instead of
`true`. `schemars = "1.0"` was already a direct dependency; no Cargo.toml
change.

`chain_types_publish_a_json_schema_naming_the_kind_discriminator` asserts
`schema_for!(Chain)` succeeds, that the schema names `kind`, that it does not
still carry a `fact` discriminator, and that all nine variant tags survive
into it. A schema that omitted a variant would let a generated client fail on
data the verifier considers valid.

## F3. Determinism

Both fixed at the query side with total orders:

- `graph::hub_nodes` sorted on degree alone, so every tie was broken by row
  order. Now degree descending, then file path, then name, then node id.
  A bare degree sort means the same repo indexed twice can report a
  different top-N, and `--limit` can silently include a different symbol.
- `graph::dependencies::matching_roots` returned roots in storage order, and
  a collided bare name emits one group per root. Now sorted on (file path,
  qualified name, node id). The per-group collections got total orders too:
  `items` was `sort_by_key(|d| d.depth)`, which ties constantly, and
  `unresolved` / `ambiguous` / `stale_references` had none at all.

`two_fresh_indexes_produce_byte_identical_query_output` indexes the polyglot
fixture four times into four isolated in-memory stores and asserts one
distinct serialization of both `rdeps` (on `connect`, which collides across
`api/app.py` and `worker/main.go`) and `hubs`. It guards against a vacuous
pass by asserting the query returned more than one group and more than one
hub.

The fix is load-bearing, checked by removing it:

```
# ordering fix reverted
$ cargo test --release --test explain two_fresh_indexes
assertion `left == right` failed: 4 fresh indexes produced 2 distinct rdeps orderings
test result: FAILED. 0 passed; 1 failed

# fix restored
test two_fresh_indexes_produce_byte_identical_query_output ... ok
```

Four indexes, two orderings, which reproduces L4's measurement exactly.

### Where the instability actually comes from

Named here because the brief asked, and because the first answer was wrong.

The initial version of this test used a different `project_id` per run and
"detected" nondeterminism it had introduced itself: node ids are
`sha256(project_id, file_path, name, node_type, start_line)` truncated to 16
bytes (`index::node_id`), so varying the project id changes every id. With
the project id held fixed, node ids are byte-identical across fresh indexes.

So the leak is not in id generation and not in anything index code chooses.
It is the order SurrealDB returns rows in, which is not stable between two
independently built stores. There is nothing to fix in `src/index/mod.rs`:
row order is the store's, and a query that depends on it is the defect. The
query-side total order is the complete fix, not a workaround for an
index-side bug still outstanding.

## F4. Chain wire version

`EXPLAIN_VERSION` 1 to 2. The `fact` to `kind` rename is an incompatible
format change: a v1 chain does not deserialize into a v2 `Fact` at all, so a
caller going straight to `serde_json::from_str` gets `missing field "kind"`.

That error is the wrong message to send. An audit deliverable exists to be
re-verified by a client months later, and "missing field" reads as "your
evidence is malformed or forged" when the truth is "this tool moved on".
Telling a client their evidence failed verification, when the real answer is
version skew, would be a false accusation dressed up as a machine check.
Nothing has persisted a chain yet, so the bump costs nothing now and cannot
be applied retroactively once a report has one saved.

Three pieces:

- `ChainVerdict` gains `unsupported_version: Option<u32>`
  (`skip_serializing_if`), so "your evidence does not hold up" and "I cannot
  read your evidence" are distinguishable rather than collapsed into one
  boolean.
- `verify_chain` checks the version before any step. A chain from another
  format may still deserialize far enough to reach it, and checking its
  steps against v2 semantics would produce confident nonsense.
- `verify_chain_json` reads the version *before* attempting the parse, which
  is the only place the v1 case can be caught at all, since a v1 document
  never becomes a `Chain`.

`an_older_chain_version_is_reported_as_unreadable_not_as_invalid` builds a
real v1 document in the pre-rename shape and asserts: a direct
`from_str::<Chain>` fails (so the trap is real, not hypothetical),
`verify_chain_json` returns `unsupported_version: Some(1)` with no step
findings, a current chain still verifies through the same entry point, a
struct claiming version 99 is gated too, and a genuinely malformed document
at version 2 is reported as a document failure (step index 0, which real
1-based steps never use) rather than a version one.
`emitted_chains_carry_the_current_explain_version` pins the stamp.

## F5. Debug struct dumps out of wire-facing verdict reasons

Found by the integration pass. `verify_chain`'s `StepVerdict::reason` is
wire-facing: it ships in JSON, an agent reads it, and a client re-verifying
an audit report may see it. Four branches were formatting a whole struct
with `{:?}`, which put Rust field syntax into a sentence meant for a person:

```
node "1d2ac43e..." is ExplainNode { node_id: "1d2ac43e...", name: "use_stale",
node_type: "function", language: "rust", file_path: "src/stale_caller.rs",
qualified_name: "stale_caller::use_stale", start_line: Some(9) }, chain
claims ExplainNode { ... }
```

`ExplainNode` and `EdgeKey` gained a compact `describe()` and the four sites
use it. The same reason now reads:

```
node 1d2ac43e... is stale_caller::use_stale (function) at src/stale_caller.rs:9,
chain claims stale_caller::use_stale_tampered (function) at src/stale_caller.rs.moved:9
```

The remaining `{:?}` uses in reasons are on `String` and `Vec<String>`, which
render as quoted text and lists rather than struct syntax; those were left.

`no_verdict_reason_contains_a_debug_struct_dump` drives every failing branch
the verifier has and asserts no reason contains a brace or a struct field
token (`node_id:`, `qualified_name:`, `from_id:`, `file_path:`,
`start_line:`, `edge_type:`, `node_type:`).

**The first version of that test was vacuous and is worth recording.** It
tampered by pointing `node_id` at a non-existent node, which takes the
earlier "no node with id" branch and never reaches the struct comparison at
all. It passed with the Debug dump still in place. Caught by reverting the
fix and expecting a failure that did not come. The test now keeps the node id
valid and changes `qualified_name` and `file_path` instead, and carries two
explicit vacuity guards asserting that the comparison branch and the
`EdgeKey` branch each actually ran, keyed on reason text rather than on the
fact tag (several branches report themselves as `node_exists`, and only one
of them ever emitted a dump).
